# 长方法结构与注释

## 读取时机

整理长方法、复杂业务流程、编排方法或方法内部代码结构前读取。简单方法、普通增删改和自解释代码不加载本规则。

```text
一、目标与边界

1. 目标是让方法的执行骨架、业务阶段和关键取舍更容易理解，不是追求注释数量或形式整齐。
2. 如果任务只是结构和注释整理，必须保持外部行为、调用关系、接口、数据、副作用和异常语义不变。
3. 优先遵守项目现有格式、语言习惯和 IDE 约定；没有统一约定时再采用本规则的推荐格式。
4. 不因方法较长就默认抽服务、拆类、引入设计模式或建立新架构；抽象必须消除真实重复或隔离明确职责。

二、注释与分区判断

1. 主流程步骤：具有明确执行阶段或业务意义时，使用步骤注释或项目支持的折叠分区；关键步骤即使只有一行，也可以独立标识，以便折叠后仍能看清完整流程。
2. 个别难懂代码：使用简短行内或行前注释，说明业务含义、原因、约束或特殊取舍。
3. 自解释代码：变量、调用和结构已经清楚时不加注释，不复述代码字面行为。
4. 同质长串：相同模式的连续赋值、映射或查表逻辑能够快速看懂时，不为长度机械分组或增加分区。
5. 异质长串：来源、职责或业务语义混杂时，按类别聚合同类代码，并使用简短分组注释；不把每个小分组都升级为折叠区。
6. 原有注释：优先保留语义准确且仍然有效的原注释；整理时只补缺失的结构说明，不用新编注释覆盖真实业务信息。
7. 重复注释、失效注释和与实现矛盾的注释应合并、更新或删除，但必须先确认真实行为。

三、折叠分区规则

1. 只有主流程阶段、有体量的独立步骤或重要业务节点才使用折叠分区；简单查表、少量赋值和零散代码不用分区。
2. 项目已使用 `region`、`editor-fold` 或语言原生分区语法时沿用现有形式，不混用多套风格。
3. Java 或 IDEA 项目没有既有约定、且用户希望使用折叠结构时，可采用中文标题：

   // region ========================= 初始化 =========================
   ...
   // endregion

4. 分区标题描述业务阶段或执行职责，不只写类名、方法名和技术名词。
5. 单个步骤超过约 50 行或展开后仍难以理解时，根据内聚性选择：抽取独立方法、增加少量子分类注释，或为明显的大子流程增加嵌套分区。
6. 轻量步骤应合并到上一级流程并用简短注释说明，避免出现一个复杂分区旁边堆积多个只有一两行的空洞分区。

四、方法与抽象判断

1. 短方法不能只按行数决定去留，应检查调用者数量、命名表达力、职责和内联后的可读性。
2. 多处复用的方法优先保留；调用少但命名本身能表达业务意图的方法可以保留；只有一个调用者且内联后更清楚时才考虑内联。
3. 长方法即使只有一个调用者，内联会破坏主流程时仍应保留。
4. 重复代码只在语义和变化原因一致时抽取；不要把简单条件路由、查表或少量分支包装成工厂、策略或多层对象。
5. 判断标准是整体可理解性、职责清晰度和维护成本，不是方法数量、行数对称或设计模式数量。

五、执行顺序

1. 先标出方法的主流程步骤和业务阶段。
2. 再识别异质长串、真实重复、难懂分支和失效注释。
3. 先做最小的分组、命名和注释调整，再判断是否确有必要抽方法。
4. 整理后从折叠态检查主流程骨架，从展开态检查每个步骤是否仍然容易阅读。
5. 对照修改前后行为，确认条件、执行顺序、异常、事务、数据写入和外部副作用没有意外变化。

六、完成检查

1. 注释说明业务原因和不明显约束，没有复述显而易见代码。
2. 分区数量与方法复杂度匹配，没有为了形式把简单代码切碎。
3. 原有准确注释得到保留，重复或失效注释已处理。
4. 没有借结构整理扩大为未经授权的架构重构。
5. 已执行语法检查、局部测试或关键路径复查；无法运行时明确未验证范围。
```
