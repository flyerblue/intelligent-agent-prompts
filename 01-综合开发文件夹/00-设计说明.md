# 智能体提示词体系设计说明

## 一、目标

本套提示词体系不是简单重写原提示词，而是在保留原有强约束的前提下，吸收 `codex-cookbook` 的核心思想，形成一套更适合长期使用的结构化智能体提示词。

目标有四个：

1. 保留你原来最重要的控制力：
   - 不要瞎猜
   - 复杂任务先计划，低风险小任务直接推进
   - 多提问、少误判
   - 查看项目文档
   - 关键逻辑补必要注释，避免机械注释
   - 任务结束后补充开发文档和长期记忆

2. 引入 `cookbook` 的核心思想：
   - 先判断场景，再决定处理方式
   - 用“目标、模式、约束、输出、验证”来收敛任务
   - 区分长期建设、阶段性过渡、短期止血
   - 缺陷修复先复现、先找根因
   - 技术债先判断是否阻塞主线，不阻塞则挂账

3. 让提示词从“单段说明”升级为“通用层 + 场景层”：
   - 通用层：适用于所有任务
   - 场景层：针对不同局面自动切换规则
   - 专项层：单独拿出来就能用
   - 全能层：一份提示词直接覆盖全部常见开发工作

4. 优先适配 Codex / OpenAI 编码代理，同时尽量兼容通用聊天模型。

## 二、底层结构

本次设计采用四层结构：

### 1. 通用层

所有任务都必须遵守的基础规则，例如：

- 先理解再执行
- 不瞎猜
- 复杂任务先计划
- 能问则问
- 查项目文档
- 不擅自编译打包
- 详细注释
- 落文档与长期记忆

### 2. 场景判断层

智能体接到任务后，先判断当前更接近哪一类场景，再套用对应规则。

本次固定为 7 类：

1. 直接开发
2. 缺陷修复
3. 需求收敛 / 计划设计
4. 代码评审 / 提交前检查
5. 项目探索 / 上下文恢复
6. 技术债记录 / 阶段性止血
7. 直接回答 / 结果交付

### 3. 场景规则层

不同场景使用不同规则，例如：

- 缺陷修复：优先复现、找根因、区分长期建设 / 阶段性过渡 / 短期止血
- 探索场景：先建立模块结构和文档上下文，不急着写代码
- 评审场景：先列问题，再给总结

### 4. 输出与收尾层

任务结束后统一要求：

- 给出约 150 字开发需求与开发结果总结
- 只有在本次结论具备长期价值或用户明确要求时，才判断是否做文档沉淀
- 项目级文档稳定分为四类：`项目总体认知`、`项目模块认识`、`项目总体日志`、`项目模块日志`

## 三、为什么要拆成“总控版 + 场景版 + 全能版”

### 1. 总控版

适合做系统提示词或主代理提示词。

特点：

- 内部自己先判断场景
- 根据场景切换规则
- 更适合 Codex 这种长期执行型代理

### 2. 场景版

适合你手动按情况挑一份直接贴。

特点：

- 结构更短
- 指令更直接
- 适合“我已经知道这次是什么任务”的场景

### 3. 全能版

适合你只维护一份长期主提示词。

特点：

- 一份即可覆盖多数任务
- 包含通用规则与自动场景切换
- 更适合作为默认常驻提示词

## 四、从原提示词升级的关键变化

### 1. 从“堆规则”改成“先判断再套规则”

原提示词的问题不是约束不够，而是结构偏平。
这次改造后，智能体会先判断任务类型，再决定问法、计划方式和执行方式。

### 2. 增加“时间尺度判断”

尤其在缺陷修复和补丁任务中，先判断这是：

- 长期建设
- 阶段性过渡
- 短期止血

这样能明显减少“为了赶紧修而把结构修坏”的情况。

### 3. 增加“探索场景”和“评审场景”

你实际工作里不只有写代码，还经常需要：

- 恢复上下文
- 看项目模块
- 读文档
- 理清结构
- 做提交前检查

这些都不应该用“直接开发”模式硬处理。

### 4. 增加“技术债挂账机制”

智能体在推进主线时发现问题，不应一律顺手大改，而要先判断：

- 是否阻塞当前交付
- 不阻塞就记账
- 阻塞再处理

## 五、面向 Codex 的适配点

本次提示词体系对 Codex 做了专门适配：

- 默认先看项目文档、目录结构、上下文
- 复杂任务先整理计划；低风险小任务可以直接推进
- 不主动执行高成本全量编译、运行、打包；允许低成本局部验证
- 允许低风险操作直接推进
- 结束后按需判断是否沉淀到四类项目文档，而不是默认补两份固定文档
- 验证优先采用局部测试、静态检查、关键路径复查、最小复现步骤或人工验收标准

同时保留对通用聊天模型的兼容表达，避免只在某一个代理上才能工作。

## 六、进一步优化后的补充层

在第一轮体系基础上，再补一层“组合式模板”和“行动前自检”，这样更适合长期实战。

### 1. 组合式模板

作用：

- 把提示词拆成可拼装的几段
- 便于后续按任务快速组合
- 避免每次都维护一整份超长提示词

建议拆成四段：

1. 通用底座
2. 场景附加
3. 归档附加
4. 模型偏好附加

### 2. 行动前自检

作用：

- 避免智能体虽然有规则，但执行时忘了最关键约束
- 在复杂任务、缺陷修复、评审、归档等场景里尤其有效

建议自检问题：

1. 我现在判断的主场景对不对
2. 当前信息是否足够，不足够要不要先提问
3. 这次是长期建设、阶段性过渡还是短期止血
4. 当前动作会不会顺手扩任务
5. 这次结论后续应该写入哪一层归档

## 七、目录结构说明

当前目录按两类拆分：

- `01-综合开发文件夹\`：放通用开发主提示词，以及设计说明、速查清单、组合模板、七类场景提示词等基础内容
- `02-专家提示词文件夹\`：放专家专项提示词，覆盖开发、重构、接口、数据库、前端、性能、排查、评审、测试、复盘、文档归档、结构初始化、陌生业务学习沉淀等场景；实际使用时按需选择，不必全部叠加

## 八、推荐使用方式

如果你想长期稳定使用，我建议：

1. 默认常驻使用 `01-综合开发文件夹\06-最终常驻版智能体提示词.md`
2. 做综合开发类任务时，再从 `01-综合开发文件夹\03-七类场景专项提示词.md` 里补对应一段
3. 如果要给长期主代理配置系统提示词，优先用 `01-综合开发文件夹\01-总控版智能体提示词.md`
4. 如果你想保留一份更完整但仍可常驻的版本，用 `01-综合开发文件夹\02-全能版智能体提示词.md`
5. 如果你想长期迭代提示词，优先从 `01-综合开发文件夹\05-组合式提示词模板.md` 里拼装和替换
6. 如果任务已经明确属于某个专家专项类型，从 `02-专家提示词文件夹\` 中选择对应文件叠加使用；专家提示词较多时，优先挑最贴近任务的一份

## 九、文档路径约定

为了避免归档规则只有概念没有落点，当前固定采用以下路径约定：

1. 全局文档固定放在：
   - `D:\1poj\学习\lw-全局文档.md`
2. 当前项目级文档固定放在：
   - `项目文档\开发记忆\项目总体认知\`
   - `项目文档\开发记忆\项目模块认识\`
   - `项目文档\开发记忆\项目总体日志\`
   - `项目文档\开发记忆\项目模块日志\`

这样设计的目的，是让“全局规则”和“项目内归档”天然分离，同时把项目文档稳定收敛到四类固定目录，避免再依赖 `lw开发文档.md`、`lw长期记忆.md` 这类混合型文档。
