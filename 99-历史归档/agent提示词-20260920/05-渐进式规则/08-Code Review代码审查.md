# Code Review 代码审查

## 读取时机

代码评审、提交前检查、PR 审查、重构验收或用户要求“看实现是否正确”时读取。只做代码审查时默认不修改实现；默认允许补充或修正必要注释，其他修改必须先获用户明确确认。

```text
一、评审目标与权限

1. 评审首要目标是确认语义正确、符合原始需求、改造范围受控、实现与项目能力匹配，并识别真实风险；不是追求更多代码、更多防御或更多设计模式。
2. 评审前读取实际 diff、原始需求和验收标准、相关项目文档、调用链、字段定义、必要配置和核心表结构；不能脱离上下文只看单行代码。
3. 每条发现都要有证据。按“已确认、基于证据的高概率问题、待用户/运行/数据库核验”标记结论，不把猜测直接写成缺陷。
4. 发现应包含：严重度、文件与行号、证据、触发条件、影响范围、建议方案、是否阻塞提交，以及是否需要用户拍板。
5. 评审默认只读。可以直接补充或修正必要代码注释，但必须保持行为、结构、接口、依赖、配置、日志和测试不变；抽方法、重排结构、改逻辑、加日志、增加防御、调整依赖或修改测试均先说明并等待确认。
6. 评审不得读取、展示或记录任务无关的密码、密钥、Cookie、Token、私钥和其他秘密；数据库和外部系统继续遵守常驻安全围栏。
7. 本文件独立包含审查标准，不默认叠加“代码质量与注释”实现规则。用户确认修复、重构或其他实现修改后，再按实际动作读取代码质量规则。

二、复杂度分级与审查编排

先根据变更范围、风险和关联程度选择一档，不机械增加审查人数：

1. 小修小改：单文件、局部逻辑、低风险、无公共契约或数据模型变化。主 Agent 快速检查明显的字段语义、需求偏差、越界加料、明显错误和验证缺口，通常不启用子代理。
2. 普通功能：一个明确功能，涉及多个方法、接口或模块，但边界清楚。按需要启用 1 至 3 个独立审查方向：字段语义、业务实现、代码质量；每个方向只读、范围不重叠，主 Agent 汇总并复核高风险结论。
3. 复杂及核心实现：核心链路、多模块关联、权限/事务/数据迁移、整个模块重构、公共组件或高风险系统。至少 3 路，可按模块或风险扩展到 10 路；独立审查需求回归、字段语义、状态与权限、数据与事务、依赖能力、质量可维护性、安全和测试等。共享文件先并行只读，任何修改必须串行且先获确认。
4. 使用 Claude MCP 或其他 Agent 时，具体权限、session、预算、超时、轮询和修复流程遵守：
   D:\1poj\学习\智能体提示词体系\05-渐进式规则\06-Claude MCP调用与Review.md
   不重复启动已有相同维度的审查；主 Agent 负责范围、证据冲突和最终结论。

三、字段与变量语义 Review

逐项追踪重要字段、变量、参数和返回值：

1. 定义位置、来源、生产者、消费者和读写方向。
2. 字段名称与真实业务含义，识别“类型正确但语义错误”“同名异义”“异名同义”和复制粘贴错位。
3. 前端字段、请求/响应 DTO、接口参数、Service 变量、Mapper 参数、实体字段和数据库列的映射。
4. 转换规则、单位、精度、时区、编码、排序、状态、枚举、默认值、空值和缺省行为。
5. 主键、外键、业务编号、显示名称、编码、状态值和时间字段是否被混用；更新、删除、关联和回写是否使用了正确字段。
6. 字段名来自相似模块、相似表或同名 JAR 类型时，必须读取定义和调用链确认，不能凭命名猜测。

输出字段语义问题时，给出“当前字段/实际应表达的含义/证据/错误触发条件/影响/建议”，并说明是否需要业务方或数据库核验。

四、需求、业务流程与实现正确性 Review

1. 将原始需求和验收条件逐条映射到入口、流程、状态变化、持久化、返回结果和外部副作用；标记已实现、部分实现、未实现、误解和无证据项。
2. 检查正常、异常、边界、重复、撤回、重试、权限不足、不存在、依赖失败和兼容路径，但只检查项目真实可能出现或有证据支持的情况。
3. 核对状态流转、权限边界、事务一致性、幂等性、并发、异常传播、数据写入、缓存失效、消息通知、文件操作和跨模块回写。
4. 检查接口契约、旧行为、公共组件、历史数据和兼容版本是否回归；新增行为是否有对应验证。
5. 检查改造范围是否越界：需求没有要求且不属于实现必需前置/后置的功能，不应混入本次变更。
6. 项目现有能力不足、依赖版本不支持或实现成本明显超出任务时，先报告能力缺口、替代方案、风险和需要用户决定的取舍；不得用随意引入新 JAR、新框架或新架构掩盖问题。

五、范围控制与“加料”审查

逐项给新增实现分类：

1. 需求必需：原始需求或验收标准明确要求。
2. 实现前置/后置必需：不做就无法正确完成主需求的输入校验、事务收束、资源释放、必要映射、错误传播或回滚动作。
3. 最小必要实现：实现主需求不可再省的局部代码。
4. 合理增强：提高健壮性、可维护性、可观测性、兼容性或行业规范，但不是主需求必需；必须告知动机、影响、验证方式和是否建议保留。
5. 用户明确要求的非常规实现：即使不常见，也按用户明确要求处理并单独标识。
6. 无关或不合理加料：与需求无关、改变业务口径、增加不必要功能、引入新层次或扩大数据/权限/外部副作用；应判为范围污染，建议移除，不得用“无某功能版”等括号或改名掩饰。
7. 合理增强也不能默认吞入主需求。除非用户已授权，评审只报告并建议，不直接保留或扩展。
8. 评审结论必须明确：哪些是“炒糖色、放香料”式的实现必需项，哪些是“加土豆、加香菜”式的可选增强，哪些是无关加料；避免把三类混成一个“优化建议”。

六、防御性、过度设计与低价值抽象

1. 按真实上游契约、项目数据、已有调用方和业务文档判断异常可能性。上游明确只会产生一种状态时，不鼓励为未经证实的多种状态写复杂分支。
2. 区分必要校验、合理健壮性和过度防御。对不存在或没有证据的业务情况，不擅自实现；需要用户补充的信息列为开放问题。
3. 检查是否为了通过测试、消除告警或“看起来健壮”而吞异常、返回伪成功、默认兜底、静默降级、放宽断言或绕开真实问题。
4. 检查一次性小函数：若函数只调用一次、只有两三行、没有独立业务语义，且命名没有明显提升意图表达，建议内联；不能为形式抽象降低可读性和可维护性。
5. 检查重复依赖、相似 JAR、错误 API、版本不兼容、无效导入、错误包名、低级配置错误、复制粘贴残留和未使用能力。
6. 检查过度设计：是否无真实变化原因却引入工厂、策略、适配器、事件总线、通用框架、额外配置或多层包装；按实际复杂度给出删除、简化或暂缓建议。
7. 检查 SOLID 使用是否恰当：职责是否清楚、替换契约是否成立、接口是否匹配消费者、核心业务是否错误依赖不稳定细节；同时识别为套用 SOLID 而产生的机械拆分、空洞接口、假想扩展点和多余依赖层。SOLID 只作为质量证据，不作为扩大本次改造范围的理由。

七、复杂度与树状可读性

1. 对复杂方法先尝试用“流程 A → 流程 B → 流程 C；流程 A 下有子流程 A-1、A-2、A-3”概括主流程。
2. 如果复杂代码无法形成清晰的树状骨架，或必须逐行解释才能理解，应报告可读性、职责混杂或认知复杂度问题，并指出最小改善方向。
3. 复杂度 Review 可读取：
   D:\1poj\学习\智能体提示词体系\05-渐进式规则\07-长方法结构与注释.md
   按该规则检查步骤分区、同质/异质长串、原注释保留、短方法抽象和超过约 50 行步骤的继续拆分。
4. 默认可直接补充必要的树状步骤注释或修正错误注释，但不得借“可读性优化”擅自抽方法、重排结构、加日志或改变行为。

八、验证与结果合并

1. 检查现有测试是否覆盖需求主路径、关键边界和本次风险；“有测试”不等于“验证充分”。
2. 必要时建议最小复现、局部测试、静态检查、接口回归、数据库只读核验、Playwright 或交叉 Review；不得未经授权执行真实写入或外部副作用。
3. 多路结果先按证据去重，再处理冲突；冲突结论回到需求、代码、调用链、配置、数据库或运行证据复核。
4. 按“阻塞提交、高风险、一般问题、建议优化、待确认”分级；风格偏好和可选增强不得冒充阻塞缺陷。
5. 最终明确：是否建议提交、必须修复项、建议修复项、允许暂留项、未解决风险、验证空白、需要用户拍板的事项和下一步。

默认输出：Review 复杂度等级与审查方式；按严重度排序的问题（文件/行号、证据、触发条件、影响、建议和确认要求）；字段语义结论；需求与业务回归结论；依赖和能力缺口；加料分类；可读性与过度设计结论；验证结果；是否建议提交；建议新增或更新的文档。
```
