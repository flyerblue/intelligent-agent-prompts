# 上下文交接

## 操作目标

在当前会话上下文接近上限、可能触发压缩或需要换新会话时，把可继续工作的事实、证据和边界写入项目文档，再由新会话先恢复并核对交接内容。此操作优先保护事实完整性，不用压缩替代交接。交接完成时必须返回可直接发给下一个 Agent 的接手提示词，并告知接手方：上下文不足时可向上一个 Agent 提问；保留可追问通道是交接形式区别于压缩的最大优点。

## 提示词正文

````text
执行“上下文交接”。本操作用于当前会话即将结束、上下文接近上限或需要换新会话时的事实交接，不等同于上下文压缩，也不展开新任务。

先判断当前模式：
- 交接方：当前会话负责整理并落盘交接文档。
- 接手方：新会话负责读取、核对交接文档并恢复上下文。
- 用户未指定时，根据“我是当前正在工作的 Agent”或“我是新会话接手 Agent”自行判断；无法判断时只问这一项。

一、交接方执行规则

1. 先确认当前项目根目录；无法确认时暂停，不创建交接文档。
2. 读取当前任务相关的项目文档、`项目文档\00-入口\文档地图.md`、`项目文档\00-入口\权威文档索引.md`（存在时）、相关开发记忆、当前代码差异和 Git 状态。只读必要范围，不一次加载全部文档。
3. 从当前会话记录和文件证据提取事实。每条内容标记为“已确认事实”“基于证据的判断”或“待确认/未知”；没有证据的内容写“没有记录”，不要凭印象补全。
4. 交接文档使用当前项目的绝对路径：
   `<项目根目录>\项目文档\开发记忆\开发过程\会话交接\YYYY-MM-DD-HHmm-上下文交接.md`
   可以在上下文尚未紧张时提前建立并增量更新；先创建缺失的“会话交接”目录；已有同一交接主题时优先更新，不覆盖其他交接文档。最终汇报实际解析后的绝对路径，不保留尖括号占位符。
5. 交接文档至少按以下结构写入：

   - 交接元信息：项目根目录、生成时间、原会话目标、交接原因、当前 Agent
   - 当前目标：要解决的问题、成功标准、范围和明确不做项
   - 当前进度：已完成、正在进行、尚未开始；正在进行项写清最后停留位置
   - 已确认事实：事实、证据来源、适用范围
   - 关键决定：决定内容、备选方案、选择原因、证据、是否可变更
   - 关键上下文：相关模块、调用链、数据流、接口/字段语义、环境或配置要点
   - 关键文件：实际读取、修改或生成的文件及其作用；不可从 Git 或代码直接恢复的说明才写详细内容
   - 验证结果：执行的命令或检查、结果、未覆盖范围；没有执行的写“未执行”及原因
   - 失败尝试：尝试方式、失败表现、失败原因、是否应再次尝试
   - 未解决事项：阻塞、风险、技术债、待用户决定和待运行/数据库/业务核验项
   - 权限与边界：已获授权、未获授权、禁止动作、不可改变的用户决定
   - 下一步：按优先级列出下一项具体行动、前置条件和验收方式
   - 接手前必须确认的问题：只列会影响正确性、范围、权限或下一步的疑问
   - 接手 Agent 读取顺序：交接文档、权威索引、相关认知/决策/成功路径/日志、代码与验证入口的绝对路径

6. 不把密码、密钥、Cookie、Token、私钥、连接串或其他秘密写入交接文档；敏感内容只记录“存在相关配置，需按安全方式核验”。
7. 不把闲聊、重复输出、可由代码或 Git 直接恢复的细节、大段原始聊天记录写入交接文档。
8. 不借交接之名修改代码、配置、依赖、真实数据或 Git；交接文档本身的创建或更新是本操作的唯一写入动作。
9. 写入后重新读取交接文档，核对目标、进度、事实、文件、验证、风险和下一步是否完整；发现矛盾时以当前代码、Git 和最新用户决定为准，并标记旧记录失效原因。
10. 交接方完成后汇报：交接文档绝对路径、写入或更新内容、已确认事实数量、待确认问题、接手 Agent 的第一步，以及是否建议立即开启新会话。不要执行 `/compact` 代替交接。
11. 汇报中必须返回可直接发送给下一个 Agent 的接手提示词（按“四、接手提示词模板”生成），至少包含任务主题、交接文档绝对路径、恢复指令和“上下文不足时可向上一个 Agent 提问”的提示；没有返回接手提示词视为交接未完成。

二、接手方执行规则

1. 先读取交接方给出的交接文档绝对路径；路径无法读取时明确说“无法读取该交接文档”，请用户提供内容或正确路径，不得按文件名猜测。
2. 再按交接文档中的“接手 Agent 读取顺序”读取必要的项目入口、权威索引、相关记忆、代码和验证入口。不要一次加载全部项目文档，也不要重新做已经有证据完成的工作。
3. 用当前代码、Git 状态和用户新要求核对交接文档。发现文档与实现、Git 或最新用户决定冲突时，列出冲突、证据和影响，暂不把冲突内容当成事实。
4. 恢复完成后先用简短内容告知用户：当前目标、已完成进度、关键决定、下一步、读取的文件路径和恢复结论。
5. 单独列出“疑问、不清楚、没有记录、需要用户确认”的项目。没有疑问时明确写“未发现影响继续工作的关键疑问”。不允许根据上下文印象替换缺失事实。
6. 上下文不足或发现交接遗漏时，可向上一个 Agent 提问：把问题按“问题、已查证来源、期望补充的事实”整理后由用户转达给交接方会话。保留对交接方的追问通道是交接形式最大的优点，提问优先于凭印象补全。
7. 只有在以下条件同时满足时才继续任务：交接文档可读取；当前目标和下一步明确；权限和不做项明确；没有未解决的关键冲突或阻塞。否则先提最关键的问题，不修改实现。
8. 接手后发现交接遗漏或事实错误时，先修订交接文档并记录修订原因；不要静默改变原结论。修订交接文档之外的任何代码、结构、配置、依赖、测试、日志、真实数据或 Git 内容，按常驻规则和当前场景权限执行。
9. 接手方完成恢复后，从交接文档列出的“下一步”开始，不重复已完成事项；如需改变目标、范围或方案，先说明变化及原因。

四、接手提示词模板

交接方在最终汇报中返回此提示词，由用户直接发送给下一个 Agent：

```text
接手任务：<任务主题>
交接文档：<交接文档绝对路径>

请先读取上面的交接文档，按其中“接手 Agent 读取顺序”恢复上下文，恢复完成后按“下一步”继续，不重复已完成事项。
上下文不足或有疑问时，把问题整理后向上一个 Agent 提问（由用户转达原会话），不要凭印象补全。
```

五、接手方首轮回复模板

```text
已读取交接文档：<绝对路径>

当前进度：<两三句话>
已确认关键决定：<列最重要的决定；没有记录的明确写“没有记录”>
下一步：<具体行动>
信息来源：<实际读取的文件绝对路径>

疑问、不清楚或没有记录：
- <问题；没有则写“未发现影响继续工作的关键疑问”>

恢复结论：可以继续 / 等待确认 / 存在冲突暂缓。
```
````
