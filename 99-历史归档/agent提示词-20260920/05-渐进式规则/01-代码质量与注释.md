# 代码质量与注释

## 读取时机

写代码、修改代码或重构前读取。代码评审不读取本文件，改读独立的 Code Review 规则。

```text
一、实现原则

1. 先确认项目语言、框架、版本、分层和既有模式，优先复用现有公共能力。
2. 改动围绕当前目标，保持职责单一、依赖方向清楚，不新增没有实际收益的抽象。
3. 新增或明显增长的方法超过约 20 行时，检查能否按职责拆分；不要为满足行数机械拆分。
4. 避免深层嵌套、不必要对象复制、隐式副作用、重复逻辑和含义不明的常量。
5. 输入、空值、边界、异常、并发、权限和兼容性按实际风险处理，不堆无依据的防御代码。
6. 保持现有公共接口和行为兼容；需要改变时先说明影响和迁移方式。

二、SOLID 原则

SOLID 用于判断职责和依赖是否合理，不是强制增加层次、接口或设计模式。优先服从当前需求、项目既有架构、可读性和 YAGNI；没有真实变化原因时保持简单。

1. 单一职责（SRP）：类、方法和模块应围绕一个清晰职责组织，只有一个主要变化原因。发现业务编排、数据转换、持久化和外部调用混在一起时，按真实边界拆分；不要把连续的小步骤机械拆成大量一次性函数。
2. 开闭原则（OCP）：对已经确认且会持续变化的扩展点保持开放，对稳定核心逻辑保持关闭。优先使用项目现有扩展机制；不要为假想需求提前创建策略、工厂、插件或通用框架。
3. 里氏替换（LSP）：子类或实现类必须遵守父类型的输入、输出、异常、副作用和状态约束，不加强前置条件、不削弱结果保证，也不通过特殊分支破坏调用方预期。
4. 接口隔离（ISP）：调用方只依赖实际需要的能力；避免臃肿接口迫使实现类提供无关方法。拆分接口必须有明确消费者或变化边界，不为形式把简单接口切碎。
5. 依赖倒置（DIP）：核心业务不直接绑定不稳定的基础设施细节；存在多个实现、外部依赖隔离或明确测试替换需求时，通过项目既有抽象反转依赖。单一且稳定的实现无需机械增加接口和注入层。
6. 原则冲突时，按业务正确性、范围控制、现有架构一致性、可读性和维护收益排序取舍，并说明为何采用或不采用某项原则。

三、注释颗粒度

1. 先判断工程长期性、协作规模和业务复杂度，不采用同一套固定注释密度。
2. 企业级、长期维护或多人协作项目：公开方法和核心方法详细说明职责、参数、返回值、异常、副作用、业务约束；方法内复杂业务流程按关键步骤注释。
3. 个人、小型或短期项目：以必要的方法级注释为主，只在关键算法、易误解分支和特殊约束处增加行内注释。
4. 注释解释“为什么、业务限制和不明显的取舍”，不复述代码字面行为。
5. 代码变化后同步更新相关注释；错误注释比缺少注释更危险。
6. 涉及长方法、复杂流程、方法内部结构整理，或需要通过分区和注释提升可读性时，再完整读取：
   D:\1poj\学习\智能体提示词体系\05-渐进式规则\07-长方法结构与注释.md

四、完成检查

1. 复查实际差异，只包含预期文件和行为。
2. 删除调试残留、无用分支、临时日志和与任务无关的格式化改动。
3. 执行与风险匹配的局部验证；无法验证时明确缺口和验收方式。
```
