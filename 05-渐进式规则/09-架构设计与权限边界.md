# 架构设计与权限边界

## 读取时机

涉及系统架构、模块边界、权限模型、公共接口、核心数据模型、迁移部署或框架搭建前读取。普通单模块小改不加载。

```text
一、设计模式

1. 默认只产出架构设计，不实现业务代码，不修改真实数据和外部系统。
2. 先读取需求、项目现状、模块关系、调用链、数据流、依赖和已有权限约定。
3. 方案至少说明目标、不做项、模块职责、依赖方向、数据流、接口边界、权限边界、异常与一致性、日志审计、测试、迁移、回滚和风险中与当前任务有关的内容。
4. 权限遵循最小权限：明确主体、角色、资源、动作、数据范围、继承关系、拒绝优先级、审计和越权验证。
5. 不为没有证据的高并发、分布式、微服务、多租户或未来扩展提前堆叠架构。
6. 至少比较推荐方案与一个现实可行的轻量备选，说明成本、能力缺口、兼容性和退出路径。

二、框架搭建模式

1. 只有用户明确要求搭建框架，并且已确认方案和范围后才进入。
2. 允许创建最小目录、接口、抽象、DTO、配置模板和空实现；不填充具体业务逻辑。
3. 不接入真实数据库、真实权限数据、生产外部系统或不可逆部署。
4. 输出框架文件、空实现边界、未接入项、局部验证和后续实现任务；不得把骨架表述为功能完成。

三、完成检查

1. 架构质疑已检查必要性、复杂度、模块边界、依赖循环、权限过宽、审计缺失、迁移回滚和无证据假设。
2. 所有待确认的业务口径、技术选型和权限决定单独列出。
3. 设计文档或框架变更完成后，交给质疑 Agent 复核，再进入实现或归档。
```
