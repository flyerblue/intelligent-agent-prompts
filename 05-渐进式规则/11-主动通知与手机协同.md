# 主动通知与手机协同

## 操作目标

在任务失败、需要用户拍板、长任务结束或需要处理用户手机回复时，通过本机通知中枢把信息送达用户手机（企业微信机器人"zcode通知"），并在合适姿态下挂起等待或继续任务。本规则只管"信息如何到达用户、回复如何取回"，不改变当前任务的主线与权限边界。

## 提示词正文

````text
执行"主动通知与手机协同"。在需要把信息送达用户手机、等待用户拍板或处理用户手机回复时按本规则操作。

一、通知中枢是什么

- 链路：push 或告警 → 发件箱队列（自动带[项目名]标签）→ 常驻中继 → 用户手机企微。中继离线时消息排队补发，调用方无需关心中继死活。
- 工具（会话已注册时）：mcp__notify__push（推送）、mcp__notify__check_inbox（取本项目手机指令）、mcp__notify__status（中枢状态）。
- 工具未注册时（旧会话、子代理）：经 Bash 启动 C:\Users\23973\.zcode\hooks\notify_mcp_server.py（stdio JSON-RPC，先 initialize，随后逐行发 tools/call 请求，每行一个 JSON、读一行回一个 JSON），效果等同工具按钮。
- push 关键参数：text（markdown 正文）、level（info 知会/warn 重要/critical 紧急）、wait_minutes（登记等待时限，分钟）、default_action（超时默认：continue 按原计划继续/halt 放弃该事项）。

二、何时必须通知（判定从严，失败宁多勿漏）

必须 push：
1. 任务失败或受阻且无替代方案——环境阻碍、依赖缺失、服务不可达、测试大面积失败、数据异常。无论任务大小，失败一律通知；"在返回文本里写失败报告"不算通知，用户可能根本不在电脑前。
2. 需要用户拍板——方案分歧、计划确认、授权请求、范围变更。
3. 长任务、后台任务、工作流结束——推送结果摘要，成功 info、失败 critical。

可裁量：里程碑进展、小任务完成、用户在场且已当面汇报的事项。
禁止打扰：正常流程内的每步操作、重复确认已确认的事实。

三、三种姿态

1. 知会型：push 后继续任务，不打断。适用于进展与结果通知。
2. 等待型：push 附编号选项并登记等待（wait_minutes，默认 30，default_action 按失误代价选：可安全继续选 continue，继续会浪费选 halt）→ 结束回合挂起，等待期间零消耗 → 下一回合开始先 check_inbox 取回复执行；超时未回时 check_inbox 会提示按默认动作处理，向用户说明超时结果后执行。禁止用轮询、sleep 或反复查询代替挂起。
3. 止损型：push（critical）说明原因、证据与已停止 → 立即停止该路径，不得换壳重试；被 loop-guard 拦截（ask/deny）后同理，换路或结束，不与守卫对抗。

四、子代理与后台任务特别条款

1. 一律视为用户离席：子代理与后台任务无法确认用户是否在电脑前，禁止依赖桌面弹窗（AskUserQuestion 等）获取拍板——用户离席时弹窗会挂死且无人知晓。
2. 失败无法继续时必须 push 手机，只写返回报告不算完成通知义务。
3. 需要拍板时：push 附编号选项并登记等待，然后返回；由主会话后续 check_inbox 接续执行。
4. 通知手段优先级：会话工具列表的 mcp__notify__* > Bash 驱动 notify_mcp_server.py > Bash 直接调 C:\Users\23973\.zcode\hooks\notify_hub.py 的 outbox_enqueue。

五、手机指令处理

1. 每回合开始、曾登记等待后、长任务或后台任务唤醒时：先 check_inbox。
2. 用户手机回复经三级路由分到各项目收件箱（引用某条告警 > @项目名 > 默认给最后告警来源），手机指令优先于当前计划内动作。
3. 取到的指令无法执行时，如实 push 说明原因，不静默忽略。
4. Bash 驱动 server 时的会话保持：单次任务内可保持进程连续调用；跨回合必须重新 initialize，不假设进程存活。

六、push 文案规范

- 首行给结论；正文写清：发生了什么、关键证据、需要的动作。
- 等待型必须带编号选项（1. xxx 2. xxx），方便手机直接回序号。
- 手机端渲染 markdown；不写内部代号和术语。

七、边界

- push 入队即视为送达（中继补发），关键操作后可用 status 复核一次，不反复确认。
- 通知是告知不是授权：push 不能替代安全围栏要求的用户明确授权。
- 本通知指 notify 中枢推送，不属于安全围栏所列外部业务调用。
````

## 与其他规则的关系

- 常驻通用规则不承载本规则的任何内容；唯一发现入口是常驻规则"五、渐进式规则与读取时机"第 11 条。hook 层（loop_guard 止损梯度、permission_notify 离席推送）是系统防线，不依赖 agent 读到本规则。
- loop-guard 止损梯度（3 通知/5-6 自动拒/7+ 弹窗）与本规则的止损型姿态互补：守卫拦调用，本规则管"何时主动叫人"。
- 上下文交接（10）时，未处理的等待登记与收件箱指令应写入交接文档的"未解决事项"。
- 红线重申（细则见提示词正文）：子代理与后台任务一律视为用户离席，失败无法继续必须 push 手机；拍板走手机 push 附编号选项，子代理禁用桌面弹窗；回合开始或登记等待后先 check_inbox。
